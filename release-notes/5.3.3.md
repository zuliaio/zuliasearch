# Zulia 5.3.3

Boolean handling is now consistent everywhere. The accepted forms are `true`, `t`, `yes`, `y`, `1` and `false`, `f`, `no`, `n`, `0`, matched case insensitively and ignoring surrounding whitespace. Where a value carries its own type, a native boolean and the numbers 1 and 0 are accepted as well.

## Breaking Changes

- **Numbers outside 1 and 0 are rejected in boolean fields instead of being silently indexed.** The value was previously compared after truncating to an int, so `1.5` indexed as true and `4294967296` indexed as false. Both now fail the store with the existing per-type error message. Unrecognized strings and other numeric values already failed the store and are unchanged.

## Improvements

- **Every zulia-data source reads booleans the way the server does.** Delimited, Excel, and JSON sources share one parser instead of each doing their own conversion. Anything outside the accepted set still reads as null, so `getBoolean(field, defaultValue)` keeps working.
- **Boolean values with surrounding whitespace are accepted.** A value such as `" true "` now stores instead of failing.

## Bug Fixes

- **Indexing, sorting, and faceting agree on what a boolean value means.** All three server paths now share one parser.
- **Excel data sources read the full set of boolean forms.** String cells went through `Boolean.parseBoolean`, so `yes`, `y`, and `1` all read as false. Numeric `1` and `0` cells read as null because there was no numeric branch. Formulas with a cached string or numeric result are now handled as well.
- **JSON data sources no longer throw on string and number booleans.** `getBoolean` delegated to `Document.getBoolean`, which threw `ClassCastException` on the string and number forms that JSON exports commonly use.
- **Delimited data sources trim whitespace around boolean values.** A custom parser can still be supplied with `withBooleanParser`.
